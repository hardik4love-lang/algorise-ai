## 1. Executive Architecture Overview

Tesla’s vehicle communication infrastructure transitioned from legacy bearer token commands to an end-to-end cryptographically signed command protocol (the **Tesla Vehicle Command Protocol**). Under this paradigm:
1. The cloud fleet API server acts solely as an encrypted transit gateway; it does not possess the vehicle's private keys.
2. Every vehicle control command (door lock/unlock, climate conditioning, trunk release, software updates) must be signed with an authorized client's private key enrolled directly into the vehicle's onboard Key-Management Gateway.
3. The vehicle validates signatures, counter freshness, and command authorization independently before broadcasting messages across internal vehicle CAN (Controller Area Network) busses.

This architecture fundamentally mitigates server-side credential leaks and unauthorized man-in-the-middle command execution.

## 2. End-to-End Command Cryptographic Handshake

### 2.1 Vehicle Key Enrollment & ECDSA P-256 Protocol
Client applications and fleet servers generate an asymmetric key pair using the NIST P-256 (`secp256r1`) curve:
- **Private Key ($d$):** Kept securely within Hardware Security Modules (HSM) or client-side secure enclaves.
- **Public Key ($Q = d \times G$):** Enrolled into the vehicle via a local NFC keycard tap or authorized owner approval in the Tesla mobile app.

```
+--------------------------------------------------------------------------+
| 1. Session Request: Client -> Vehicle Gateway                            |
|    - Payload: Ephemeral ECDH Public Key (Client)                         |
|                                                                          |
| 2. Session Response: Vehicle Gateway -> Client                           |
|    - Payload: Ephemeral ECDH Public Key (Vehicle), 16-Byte Random Nonce, |
|               Current Sequence Counter                                   |
|                                                                          |
| 3. Shared Secret Derivation:                                             |
|    - SS = ECDH(ClientPriv, VehiclePub)                                   |
|    - K_enc, K_auth = HKDF-SHA256(SS, Salt=Nonce, Info="Tesla-Command-V1")|
|                                                                          |
| 4. Signed & Authenticated Command Transmission:                          |
|    - Ciphertext = AES-128-GCM(K_enc, ProtobufCommandPayload)             |
|    - Tag = HMAC-SHA256(K_auth, Ciphertext + Counter)                     |
+--------------------------------------------------------------------------+
```

### 2.2 Replay Protection Invariants
To guarantee that commands cannot be captured and replayed at a later time:
1. **Monotonic Sequence Counter:** The vehicle maintains a strictly increasing counter for each enrolled key. Any incoming command where $\text{Counter}_{\text{rx}} \le \text{Counter}_{\text{vehicle}}$ is immediately discarded.
2. **Freshness Window ($\Delta t$):** Ephemeral session handshakes expire after **10 seconds**. Commands arriving outside this temporal window require a fresh handshake round-trip.
3. **Explicit Nonce Invalidation:** Nonces generated by the vehicle are single-use and invalidated immediately upon first signature evaluation, preventing parallel replay race conditions.

## 3. Telematics Gateway OAuth 2.0 PKCE & mTLS Boundaries

### 3.1 Mutual TLS (mTLS) Fleet Authentication
Partner fleet servers communicating with Tesla's Fleet API must authenticate using mutual TLS:
- Client certificates must be signed by an authorized CA registered with Tesla Partner Management.
- TLS 1.3 is enforced with forward-secret cipher suites (`TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`).

### 3.2 Scoped Authorization Tokens
OAuth 2.0 access tokens granted to fleet partners are bound to specific capability scopes:
- `vehicle_device_data`: Read-only telemetry (battery state, odometer, location).
- `vehicle_cmds`: Basic non-hazardous commands (HVAC, flash lights, honk horn).
- `vehicle_charging_cmds`: Charge port control and schedule setting.

Hazardous vehicle operations (e.g. key enrollment, immobilizer bypass) cannot be executed via cloud telematics alone and require physical cryptographic key authorization inside the vehicle.

## 4. Vehicle Gateway ECU CAN-Bus Firewall Isolation

### 4.1 Domain Separation Architecture
The vehicle's central Gateway ECU acts as an air-gap and firewall between the Telematics Control Unit (TCU) / Infotainment system (MCU) and critical powertrain/chassis busses:

```
[Cellular / WiFi / BLE Antenna]
             |
   [Telematics Gateway (TCU / MCU)]
             |
  === Gateway Firewall / IDS === (Restricted SPI / Ethernet)
             |
    +--------+--------+
    |                 |
[Body CAN]      [Vehicle CAN]  -- (Powertrain, Drive-by-Wire, Brakes)
(Doors, Lights)        |
                 [Safety Lockout: Dropped if Speed > 0 km/h]
```

### 4.2 Speed-Gated Safety Rules
The Gateway ECU enforces strict hardware and firmware state machine rules:
1. **Dynamic Speed Lockout:** High-privilege actuators (such as park pawl release, frunk unlatch, or high-voltage contactor disconnects) are hardware-inhibited by the gateway whenever vehicle velocity $v > 0\text{ km/h}$.
2. **Rate Limiting & Flooding Defense:** Telematics message throughput to Body CAN is capped at **20 messages per second** to prevent bus saturation and denial of service against safety-critical ECUs.
